# Git / GitHub — Cheat Sheet macOS

## 🧠 Le minimum à retenir

Si tu ne dois retenir que quelques commandes :

```
# Où en suis-je ?
git status

# Qu'est-ce que j'ai modifié ?
git diff

# Qu'est-ce qui sera commité ?
git diff --staged

# Préparer
git add fichier

# Enregistrer localement
git commit -m "Description"

# Envoyer
git push

# Récupérer les informations du remote sans intégrer
git fetch

# Récupérer et intégrer
git pull
```

Pour comprendre Git :

```
                 LOCAL
┌──────────────────────────────────┐
│                                  │
│ Working tree                     │
│       │                          │
│       │ git add                  │
│       ▼                          │
│ Staging / Index                  │
│       │                          │
│       │ git commit               │
│       ▼                          │
│ Commit ← HEAD                    │
│       │                          │
└───────┼──────────────────────────┘
        │ git push
        ▼
      REMOTE
        │
        ▼
   origin/main
```

Et pour comparer avec le remote :

```
git fetch
git log HEAD..origin/main --oneline
git log origin/main..HEAD --oneline
git diff HEAD origin/main
```

**Le réflexe Git n°1 :**

```
git status
```

Avant de faire quelque chose de destructeur, vérifier d'abord ce que Git pense être l'état du repository.

Cette version est maintenant plus rigoureuse sur `HEAD`, `origin/main`, `fetch/pull`, `reset`, les conflits et les suppressions, sans transformer la fiche en manuel Git complet.

## 1. Le modèle mental

Git fonctionne notamment avec trois zones principales, plus les références vers les commits et les remotes :

```
Fichiers sur le Mac
      │
      │ git add
      ▼
Staging / Index
      │
      │ git commit
      ▼
Commit local ← HEAD
      │
      │ git push
      ▼
Remote / GitHub ← origin/main
```

À retenir :

```
working tree → staging → commit → remote
```

### Les concepts essentiels

- **Working tree** : fichiers actuellement présents dans le répertoire de travail sur le Mac.
- **Staging / Index** : contenu préparé pour le prochain commit.
- **Commit** : snapshot enregistré dans l'historique Git.
- **HEAD** : référence vers le commit actuellement checkouté.
- **main** : branche locale appelée `main`.
- **origin/main** : référence locale de suivi indiquant où se trouve `main` sur le remote `origin`, selon le dernier `fetch`.
- **origin** : nom généralement donné au remote principal, souvent GitHub.

### Git ≠ GitHub

```
Git
→ système de contrôle de version
→ fonctionne localement
→ commits, branches, tags, historique…

GitHub
→ service distant
→ héberge des repositories Git
→ permet notamment de partager et collaborer
```

Important :

```
git commit
→ enregistre localement

git push
→ envoie les commits vers le remote
```

Un `commit` n'est donc **pas encore sur GitHub** tant qu'il n'a pas été poussé.

## 3. Voir les différences

### Modifications pas encore ajoutées

```
git diff
```

→ différences entre le **working tree** et le **staging/index**.

```
working tree ↔ staging
```

### Modifications préparées

```
git diff --staged
```

→ différences entre le **staging/index** et `HEAD`.

```
staging ↔ HEAD
```

### Différence entre deux commits

```
git diff COMMIT1 COMMIT2
```

Exemple :

```
git diff abc123 def456
```

### Différence entre un commit et `HEAD`

```
git diff COMMIT HEAD
```

### Différence entre les deux derniers commits

```
git diff HEAD~1 HEAD
```

### Comparer le local avec le remote

Mettre d'abord à jour les références du remote :

```
git fetch
```

Puis :

```
git diff HEAD origin/main
```

→ compare le contenu de `HEAD` avec celui de `origin/main`.

### Résumé d'un diff

```
git diff --stat
```

Pour le staging :

```
git diff --staged --stat
```

### Résumé

```
git diff
    working tree ↔ staging

git diff --staged
    staging ↔ HEAD

git diff COMMIT1 COMMIT2
    commit ↔ commit

git diff HEAD origin/main
    commit local ↔ référence du remote
```

## 4. `HEAD`

`HEAD` est une **référence vers le commit actuellement checkouté**.

Voir le commit courant :

```
git show HEAD
```

Voir le commit précédent :

```
git show HEAD~1
```

Voir deux commits auparavant :

```
git show HEAD~2
```

Voir un commit précis :

```
git show COMMIT
```

Résumé d'un commit :

```
git show --stat COMMIT
```

Voir uniquement le message et les informations principales :

```
git log -1
```

### Ajouter un fichier

```
git add fichier
```

```

```

### Supprimer un dossier du Mac et préparer sa suppression

```
git rm -r dossier
```

Puis :

```
git commit -m "Remove fichier"

```

### Supprimer de Git mais garder sur le Mac

Fichier :

```

```

```

```

Puis :

```
git commit -m "Stop tracking fichier"
git push
```

**Important :**

`.gitignore` ne retire pas automatiquement un fichier déjà suivi par Git.

## 7. `rm` vs `git rm`

### Avec macOS

```
rm fichier
```

Git détectera ensuite :

```
deleted: fichier
```

Puis :

```
git add fichier
```

ou, pour enregistrer les suppressions/modifications de fichiers déjà suivis :

```
git add -u
```

Puis :

```
git commit
```

### Avec Git

```
git rm fichier
```

→ supprime le fichier du Mac  
→ prépare également sa suppression dans Git.

Pour un dossier :

```
rm -r dossier
```

ou :

```
git rm -r dossier
```

### À retenir

```
rm fichier
→ macOS supprime
→ Git constate ensuite la suppression

git rm fichier
→ macOS supprime
→ Git prépare immédiatement la suppression
```

## 8. `.gitignore`

Exemple :

```
.DS_Store
.claude/
node_modules/
.env
dist/
build/
*.tmp
*.log
```

### Créer

```
touch .gitignore
```

### Modifier

```
nano .gitignore
```

### Vérifier pourquoi un fichier est ignoré

```
git check-ignore -v fichier
```

### Important

`.gitignore` indique à Git quels fichiers **non suivis** doivent être ignorés.

Il ne retire pas du suivi un fichier déjà suivi ou déjà commité.

Dans ce cas :

```
git rm --cached fichier
```

Puis :

```
git commit -m "Stop tracking fichier"
git push
```

### Exemple

Si `.env` contient des secrets :

```
.env
```

Mais si `.env` a déjà été commité, ajouter `.env` à `.gitignore` **ne suffit pas**.

Il faut au minimum :

```
git rm --cached .env
git commit -m "Stop tracking .env"
git push
```

Et si le secret a déjà été poussé, il faut également considérer ce secret comme compromis.

## 9. Annuler des modifications

### Annuler les modifications d'un fichier non staged

```
git restore fichier
```

→ restaure le fichier depuis l'index  
→ les modifications du working tree sont perdues.

Pour restaurer explicitement depuis `HEAD` :

```
git restore --source=HEAD fichier
```

⚠️ Ces commandes peuvent supprimer des modifications locales non commitées.

### Annuler un `git add`

```
git restore --staged fichier
```

→ retire le fichier du staging  
→ conserve les modifications sur le Mac.

### Annuler le staging de tout

```
git restore --staged .
```

Les modifications restent dans le working tree.

### Annuler un commit local

Si le commit n'a pas encore été partagé :

```
git reset --soft HEAD~1
```

→ supprime le commit de l'historique local  
→ conserve les modifications  
→ les modifications restent **staged**.

### Annuler le commit mais garder les modifications non staged

```
git reset HEAD~1
```

Par défaut, `reset` utilise le mode `mixed`.

→ supprime le commit  
→ conserve les modifications  
→ retire les modifications du staging.

### Annuler un commit déjà partagé

Préférer :

```
git revert COMMIT
```

Puis :

```
git push
```

`revert` crée un **nouveau commit** qui annule les changements du commit ciblé.

## 10. ⚠️ Commandes dangereuses

### Supprimer les modifications d'un fichier

```
git restore fichier
```

### Supprimer les modifications et le staging

```
git reset --hard HEAD
```

⚠️ Peut supprimer définitivement des modifications locales non commitées.

### Supprimer des fichiers non suivis

```
git clean -n
```

→ montre ce qui serait supprimé.

Puis, si tu es certain :

```
git clean -f
```

⚠️ Supprime les fichiers non suivis.

Pour inclure les dossiers non suivis :

```
git clean -fd
```

⚠️ Très destructeur. Toujours commencer par :

```
git clean -n
```

### Règle

Ne pas utiliser :

```
git reset --hard
git clean -f
git clean -fd
```

sans savoir exactement ce qui va être supprimé.

## 12. Tags / versions

Un **tag** marque un commit précis.

```
branche
   │
   ├── commit
   ├── commit
   ├── commit ← tag v1.0.0
   └── commit
```

```
branche → évolue avec les commits

tag → référence un commit précis
```

### Voir les tags

```
git tag
```

### Créer un tag simple

```
git tag v1.0.0
```

### Créer un tag annoté

Recommandé pour une release :

```
git tag -a v1.0.0 -m "Version 1.0.0"
```

### Voir un tag

```
git show v1.0.0
```

### Envoyer un tag sur GitHub

```
git push origin v1.0.0
```

### Envoyer tous les tags

```
git push --tags
```

### Supprimer un tag local

```
git tag -d v1.0.0
```

### Supprimer un tag sur le remote

```
git push origin --delete v1.0.0
```

### Workflow release

```
git status
git commit -m "Prepare release 1.0.0"
git tag -a v1.0.0 -m "Version 1.0.0"
git push
git push origin v1.0.0
```

## 13. Local vs GitHub

### `main`

```
branche locale
```

### `origin/main`

```
référence locale de suivi de origin/main
```

Ce n'est pas directement la branche distante elle-même : c'est la référence locale que Git utilise pour mémoriser l'état du remote connu lors du dernier `fetch`.

### Mettre à jour les informations du remote

```
git fetch
```

### Voir les commits présents sur le remote mais pas localement

```
git log HEAD..origin/main --oneline
```

### Voir les commits locaux pas encore sur le remote

```
git log origin/main..HEAD --oneline
```

### Voir les différences de contenu

```
git diff HEAD origin/main
```

### Résumé

```
HEAD..origin/main
→ commits présents dans origin/main mais pas dans HEAD

origin/main..HEAD
→ commits présents dans HEAD mais pas dans origin/main
```

## 14. `fetch` vs `pull`

### `git fetch`

```
git fetch
```

→ récupère les nouvelles informations du remote  
→ met à jour les références `origin/...`  
→ ne modifie normalement pas le working tree ni ta branche courante.

Exemple :

```
Avant :

main       A---B
origin/main A---B

GitHub avance :

A---B---C---D

Après git fetch :

main       A---B
origin/main A---B---C---D
```

### `git pull`

```
git pull
```

→ effectue un `fetch`  
→ puis intègre les changements du remote dans la branche courante.

Selon la configuration, l'intégration peut utiliser un **merge** ou un **rebase**.

### Inspecter avant d'intégrer

```
git fetch
git status
git log HEAD..origin/main --oneline
```

Puis, si tout est clair :

```
git pull
```

### Réflexe utile

Si tu veux **voir avant de modifier ta branche** :

```
git fetch
```

est généralement plus sûr que :

```
git pull
```

## 18. Conflit Git

Un conflit peut apparaître après un :

```
git pull
```

ou :

```
git merge
```

ou :

```
git rebase
```

### Voir les fichiers concernés

```
git status
```

Dans un fichier, Git peut afficher :

```
<<<<<<< HEAD
version A
=======
version B
>>>>>>> autre-branche
```

Les marqueurs indiquent les deux versions en conflit.

### Résoudre

Modifier le fichier pour conserver la bonne version et supprimer les marqueurs :

```
<<<<<<<
=======
>>>>>>>
```

Puis :

```
git add fichier
```

### Après un merge

```
git commit
```

### Après un rebase

```
git rebase --continue
```

### Abandonner un rebase

```
git rebase --abort
```

### Abandonner un merge

```
git merge --abort
```

### À retenir

```
conflit
   ↓
git status
   ↓
corriger les fichiers
   ↓
git add
   ↓
terminer l'opération
```

## 21. ⚠️ À ne jamais commiter

Ne jamais commiter :

- mots de passe
- clés privées
- tokens
- API keys
- secrets
- fichiers `.env` contenant des secrets
- certificats ou fichiers de credentials privés
- données personnelles sensibles
- fichiers inutiles ou très volumineux

### Important

Supprimer un secret du dernier commit ne suffit pas forcément.

Une donnée committée peut rester présente dans :

```
historique Git
    ↓
anciens commits
    ↓
clones / forks / backups
```

### Si un secret a été exposé

Réflexe immédiat :

```
1. Révoquer / remplacer le secret.
2. Supprimer le secret du code.
3. Nettoyer l'historique si nécessaire.
4. Vérifier les conséquences de l'exposition.
```

**Considérer un secret poussé sur un remote comme compromis**, même si le fichier est ensuite supprimé.

Le nettoyage de l'historique est une opération distincte de la simple suppression du fichier.
